# FQ4-PLAN-015 — 부대 종족 종류 제한 확장 계획

- 작성일: 2026-09-13
- 상태: **사용자 확인 대기**
- 선행 상태: PLAN-014는 사용자 요청으로 보류
- 현재 제한: 한 부대에 최대 10종류의 종족
- 목표값: 부대 정원과 같은 최대 18종류
- 현재 작업 ROM: `work/fq4/rom/current.bin`

- 완료 문서 예정: `docs/fq4/finish/015-party-race-limit-expansion.md`

## 1. 목적

한 부대에 약 18명을 배치할 수 있지만 서로 다른 종족은 최대 10종류까지만 편성할 수 있는 시스템 제한을 18종류까지 확장한다.

숫자 `10`을 단순히 `18`로 바꾸기 전에 제한이 다음 구조와 연결돼 있는지 확인한다.

- 편성 가능 여부를 판정하는 비교 상수
- 부대별 종족 ID 목록 또는 bitset
- 종족별 인원수·상태 배열
- 전투 배치와 이동 시 임시 work buffer
- AI, 합류, 분리, 교섭과 포로 처리
- 저장 데이터와 메모리카드 구조
- 편성 화면의 표시 칸과 오류 메시지

## 2. 목표 동작

- 한 부대 정원이 허용하는 범위에서 최대 18명이 모두 서로 다른 종족이어도 편성된다.
- 같은 종족 여러 명 편성과 기존 10종 이하 편성은 그대로 작동한다.
- 11번째부터 18번째 종족을 추가할 때 거부 메시지나 강제 교체가 발생하지 않는다.
- 지도 이동, 전투 진입·종료, 부대 합류·분리와 세이브·로드 후 종족 구성이 유지된다.
- 부대 인원 정원 자체는 변경하지 않는다.

## 3. 승인 범위

- 250826 기반 현재 실행 파일과 데이터에서 종족 제한 판정 경로를 추적한다.
- UI에 표시되는 제한 메시지와 관련 문자열 참조를 출발점으로 코드 호출 관계를 찾는다.
- `10`, `0x0A`, 반복 10회와 10칸 배열 후보를 정적·런타임으로 구분한다.
- 실제 편성 시 종족 ID를 수집·중복 검사·저장하는 함수와 buffer 크기를 확인한다.
- 단순 상수 변경으로 충분한지, 배열·구조 확장이 필요한지 판정한다.
- 안전한 경우 최대 18종류로 변경한다.
- 일반 BIOS에서 바로 실행되는 `current.bin`에 변경을 적용하고 전체 EDC/ECC를 유지한다.
- Python GUI와 단일 EXE 반영은 게임 수정이 검증된 뒤 별도 계획으로 진행한다.

PLAN-014의 미래 xdelta 자동 호환 기능은 이번 작업에 포함하지 않는다.

## 4. 조사 절차

### A. 제한 메시지와 데이터 흐름

1. 250826 실행 파일과 데이터에서 `종족`, `10`, 편성 실패 문구에 해당하는 코드열을 찾는다.
2. 해당 문자열을 표시하는 함수의 호출자를 추적한다.
3. 편성 후보 캐릭터의 종족 ID가 어느 구조체 field에서 읽히는지 확인한다.
4. 현재 부대에서 서로 다른 종족을 세는 loop와 비교 분기를 찾는다.
5. 10종에서 실패하는 정확한 branch와 반환값을 기록한다.

### B. 저장 구조와 buffer 크기

- 종족을 bitset으로 관리하면 지원 가능한 ID 범위와 bit 폭을 확인한다.
- 고유 종족 목록 배열이면 실제 할당 크기와 인접 field를 확인한다.
- 부대 구조체가 종족별 10칸 상태를 영구 저장하는지, 편성 시 임시 계산만 하는지 구분한다.
- stack local 배열이면 stack frame과 최대 18항목 사용 시 경계를 검사한다.
- 전역 배열이면 다른 부대나 UI buffer와 겹치지 않는 확장 위치를 확보한다.
- 메모리카드에는 캐릭터 구성만 저장하고 종족 목록을 재계산하는지 확인한다.

### C. 관련 경로 전수 조사

편성 외에도 같은 제한값이나 구조를 사용하는 다음 경로를 확인한다.

- 새 캐릭터 합류
- 부대 간 캐릭터 이동
- 부대 합병과 분리
- 교섭·포로·고용
- 전투 참가자 생성
- AI 부대 생성
- 이벤트에 의한 강제 편성
- 세이브·로드 후 부대 재구성

## 5. 구현 선택

조사 결과에 따라 가장 작은 안전한 방식을 선택한다.

### 유형 1: 단순 비교 제한

내부 구조가 이미 18명 전체를 순회하고 종족 수만 `10`과 비교한다면 비교 상수를 `18`로 변경한다.

### 유형 2: 10항목 임시 배열

종족 ID 또는 count를 10칸 임시 배열에 저장한다면 18칸을 확보하고 loop bound, 초기화와 참조 범위를 함께 변경한다. 기존 stack frame에 공간이 없으면 검증된 code cave의 별도 scratch 영역을 사용한다.

### 유형 3: 영구 구조체 또는 세이브 형식

부대 구조체나 저장 데이터가 10종을 고정 저장한다면 구조 크기를 즉시 늘리지 않는다. 캐릭터 18명의 종족 ID에서 필요할 때 고유 종족 수를 다시 계산하는 우회 함수를 우선 검토한다. 세이브 형식 변경이 불가피하면 이번 단계에서 중단하고 별도 호환 계획을 작성한다.

## 6. 런타임 검증 시나리오

가능하면 세이브 상태 또는 디버거 개입으로 서로 다른 종족의 캐릭터 18명을 준비하고 다음 경계를 검사한다.

| 종족 종류 | 기대 결과 |
|---:|---|
| 9 | 기존과 동일하게 허용 |
| 10 | 허용 |
| 11 | 새로 허용 |
| 17 | 허용 |
| 18 | 허용 |
| 19 또는 정원 초과 | 기존 인원 정원 규칙으로 거부 |

각 경우에 대해 편성 판정 반환값, 부대 인원, 고유 종족 수와 인접 메모리 guard를 기록한다.

## 7. 회귀 검증

- 같은 종족 18명과 18종족 18명을 각각 검사한다.
- 지도에서 부대를 반복 이동한다.
- 전투 진입·종료 후 18명의 캐릭터와 종족을 비교한다.
- 부대를 나눴다가 다시 합친다.
- 교섭, 고용 또는 이벤트 합류를 검사한다.
- 세이브 후 게임을 재시작하고 로드해 구성을 비교한다.
- AI 부대와 적 부대 생성이 손상되지 않는지 확인한다.
- 일반 BIOS 글꼴 적재와 한글 메뉴 표시가 유지되는지 확인한다.
- 전체 43,002개 sector의 sync, header, subheader, EDC, P와 Q 오류가 0인지 확인한다.

화면과 입력 자동화로 18종족을 실제 준비하지 못하면 판정 함수의 실제 런타임 경로를 데이터 개입으로 검사하고, 정상 플레이 최종 확인은 사용자 항목으로 분리한다.

## 9. 통과 기준

- 제한 판정과 관련 buffer의 실제 구조가 확인된다.
- 최대 18종류 편성이 인접 메모리 손상 없이 허용된다.
- 19번째 또는 인원 정원 초과는 기존 정원 규칙에 따라 안전하게 처리된다.
- 이동, 전투, 합류·분리와 세이브·로드 후 구성이 유지된다.
- 기존 10종 이하 동작과 AI·이벤트 부대가 유지된다.
- 일반 BIOS 한글 표시와 전체 글꼴 loader가 유지된다.
- 전체 디스크 EDC/ECC 오류가 0이다.
- 원본 입력이 보존되고 전체 작업 ROM 한 개 조건을 지킨다.
